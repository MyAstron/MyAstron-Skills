# Guía de estilo personal de documentación y proyecto

## Objetivo

Definir la identidad documental y visual que se usará en futuros proyectos para que cada README, manual y flujo de trabajo se sienta como algo propio, moderno y consistente.

## Tono de redacción

El estilo debe ser:

- claro
- profesional
- cercano
- técnico sin ser árido
- natural y auténtico

### Principios de redacción

- Explica con contexto antes de entrar en detalle
- Usa lenguaje directo, no artificial
- Separa lo importante de lo secundario
- Evita la repetición innecesaria
- Prioriza la comprensión del usuario

### Ejemplo de tono

Correcto:

> Este proyecto permite ... con el objetivo de ... La estructura está diseñada para facilitar ...

No recomendado:

> El programa ofrece múltiples funcionalidades útiles con gran variedad de módulos y componentes.

## Estructura recomendada para documentos

Todo README o manual debe seguir esta lógica:

1. Título claro y memorable
2. Resumen del proyecto
3. Objetivo y contexto
4. Problema que resuelve
5. Funcionalidades principales
6. Estructura del proyecto
7. Requisitos y ejecución
8. Uso básico
9. Arquitectura o flujo principal
10. Limitaciones y mejoras futuras
11. Autor / contexto del proyecto

## Estética visual

### Paleta sugerida

- fondo oscuro / neutro
- acentos azul, cyan o índigo
- verde para éxito o validación
- naranja para advertencia
- gris para arquitectura y documentación técnica

### Buenas prácticas

- Usa títulos y subtítulos con jerarquía clara
- No saturar la documentación con demasiados badges
- Usa bloques de código con claridad
- Prioriza legibilidad sobre exceso visual
- Los diagramas deben ser entendibles en segundos

## Estilo de secciones

### README

- debe vender la idea del proyecto
- debe dar contexto rápido
- debe mostrar la estructura de forma legible
- debe invitar a probar o entender el sistema

### Manual técnico

- explicación de módulos
- flujo de lógica
- responsabilidades de cada parte
- decisiones de arquitectura y restricciones

### Manual de usuario

- no debe hablar como si el usuario fuera técnico
- debe mostrar pasos claros
- debe explicar acciones con lenguaje natural
- debe centrarse en la utilidad del sistema

## Principio central

El documento debe reflejar que el proyecto fue pensado por una persona que entiende:

- la necesidad real del usuario
- la lógica del software
- la complejidad del sistema
- la importancia de la claridad

Es decir: funcional, ordenado y con identidad propia.
